# Primitive Admission Criterion

Purpose
- Prevent the ontology from drifting into a labeled toolbox.
- Distinguish first derived structural necessities from useful but non-canonical helpers.
- Make explicit that current primitive files usually mean **kernel-resolution primitive handles**, not additional deepest ontological primitives alongside change.

A candidate primitive is admissible only if all of the following are shown.

## 1. Necessity under derivation
An earlier accepted layer cannot continue coherently without distinguishing this operator or structural contrast.

## 2. Irreducibility at kernel resolution
The candidate cannot be rewritten without loss as a collapsed composition of already-admitted primitives at the current kernel resolution.

## 3. Distinct explanatory role
The candidate resolves a real structural tension in the derivation rather than serving as a mere engineering convenience or tuning knob.

## 4. Operational consequence
Introducing the primitive changes what a valid kernel can detect, preserve, compose, or reopen.

## 5. Falsifiability / ablation criterion
It must be possible to say what would show that the primitive is redundant, misplaced, or wrongly introduced.

## 6. Honest status labeling
Until the above is demonstrated, the candidate must be labeled as one of:
- `candidate primitive`
- `derived-but-contingent operator`
- `experimental handle / implementation proxy`

Working rule
- A primitive is not admitted because it helps on a benchmark.
- A primitive is not admitted because it is intuitively attractive.
- A primitive is not admitted because it is a useful control surface.

A primitive is admitted only when it is derivationally forced, non-redundant, behaviorally consequential, and ablatable.
