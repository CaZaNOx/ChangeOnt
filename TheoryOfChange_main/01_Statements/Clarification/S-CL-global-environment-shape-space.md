# The environment is a global regime-shape space that places kernel unfolding at a relevant abstraction level
## Content
The environment/shape is not a second solver, a family-local heuristic table, or a hidden planner. It is a compressed placement of a concrete problem-region into a global regime-space describing what kinds of persistence, revision, hiddenness, burden, coupling, and lawful continuation are already stabilized at the relevant abstraction level. The kernel remains the thing that unfolds. The translator only states the concrete problem semantics in common terms—this is a wall, this is legal, this is hidden, this is the current anchor or direction of better—and the environment then specifies what kinds of unfolding are legitimate there. In the full ontology, all problems are stabilized nested regions of change. In practice, we do not let the kernel build an entire world; we place it into the relevant local regime of an already-stabilized world-region and let it unfold under those lawful constraints.

## Clarification
- The environment is global: all admitted problems must be placeable in the same regime-space rather than in separate family-local maps.
- The environment is not the translator: the translator provides semantic interpretation of the problem state; the environment gives the regime-location of that interpreted state.
- The environment is not the action policy: it does not say "go LEFT" or "arm 2 is optimal." It says what kinds of stabilization, carry-forward, reopening, or local trust are legitimate.
- The environment is not identical to the raw basis vectors. The vectors span the regime-space; the environment is the placed region in that space.
- The environment should be detailed enough to prevent solving the wrong proxy problem, but not so detailed that every problem-instance becomes its own bespoke map.

## Why this follows from the ontology
If change is primary, then a concrete problem is not something outside change; it is already a stabilized region of unfolding with admissible transitions, exclusions, and retained constraints. A kernel meant to approximate unfolding change cannot be dropped into such a region without any placement information, because then it may stabilize the wrong object or treat derived constraints as if they were absent. The environment therefore records what kinds of continuation are lawful at the abstraction level we care about. That is why environment placement is not optional tuning but part of the bridge from ontology to finite operational use.

## Kernel relationship
Environment placement should modulate the lawful room in which kernel primitives and elements may unfold. A vector therefore does not usually map one-to-one to a single primitive or element. Instead, each vector changes the legitimacy of several tendencies at once—for example how much carry-forward is justified, how much rival maintenance should remain alive, how much local progress can be trusted, how easily revision should fire, or how much hidden structure should keep collapse provisional.

## Placement consequence
If the environment basis is lawful, then three things should hold.
- For any admitted problem, a fixed admissible procedure should produce a region in the shared vector space rather than a handwavy placement.
- If a problem is deformed along a real vector direction, the placed region should move correspondingly rather than arbitrarily.
- Updated placement should outperform or at least match stale placement often enough and systematically enough that the map is doing real explanatory work.

## Warning
A useful environment is not the same thing as a final or metaphysically complete map. The current vector set is a bridge-level working basis. It is acceptable for it to be coarse. It is not acceptable for it to be family-local, oracle-dependent, or so underdefined that placement becomes rhetorical.
