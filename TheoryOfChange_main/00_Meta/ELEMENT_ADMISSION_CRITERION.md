# Element Admission Criterion

Purpose
- Distinguish ontological composites from control gadgets, helpers, and implementation scaffolding.

An element is legitimate only when all of the following are shown.

## 1. Ontological bundle
It bundles lower-level CO-derived primitives/operators into a recognizable structural role that the ontology itself makes thinkable or necessary.

## 2. Not merely a strategy
The candidate is not just a useful policy mechanism, routing trick, arbitration gadget, or engineering convenience.

## 3. Primitive/operator traceability
The element must name the exact kernel-primitive/operator bundle on which it depends. It is one level up from kernel primitives, not a sibling notion.

## 4. Distinct behavioral effect
There must be a characteristic behavioral difference expected if the element is present versus absent.

## 5. Code humility
The code embodiment is one operational realization of the role, not the definition of the role itself.

## 6. Honest status labeling
Until derivation is complete, mark the candidate as:
- `canonical element`
- `provisional element`
- `experimental control surface`
- `helper / support surface`

Working rule
If a component is structurally demanded by the ontology, it may be an element.
If it is only a helpful policy mechanism, it should not be promoted to element status without further derivation.
