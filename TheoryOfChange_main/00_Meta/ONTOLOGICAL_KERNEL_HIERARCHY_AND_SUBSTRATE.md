# Ontological primitive, derived necessities, kernel primitives, elements, and substrate

This note fixes a recurrent category confusion in the project.

## 0. Two strands before the hierarchy
The hierarchy below sits mainly on the **ontological continuation** strand. It does not replace the **epistemic bootstrap** strand that licenses the ontology from the standpoint of the doubtful subject. The subjective strand earns the right to posit primacy of change; the hierarchy below then clarifies the levels used once that primacy is in play.

## 1. Ontological primitive
At the deepest level the project admits only one ontological primitive:
- **change**

Everything else must be derived from it.

## 2. First derived ontological necessities
These are not additional primitives in the deepest sense. They are the earliest structural necessities that follow once change is taken as primary. Typical examples in the current chain are:
- non-total-erasure
- trace-retention
- selective recurrence
- invariant-regime
- border/localization
- identity-through-change
- similarity
- identity-admissibility
- local comparability
- self-propagating selective retention
- remaining transformation burden
- operative difference
- operative invariant
- regime signature
- minimal adequate representation
- thin collapse law
- regime-shape variation
- transport need

These belong to the ontology-side derivation, not yet to kernel packaging.

## 3. Kernel primitives
Kernel primitives are **not** the earliest ontological distinctions. They are the first reusable finite handles at kernel resolution for operating on already-derived ontological structure. They should be admitted only when:
- a lower-level necessity has already been derived,
- the kernel repeatedly needs a compact handle for it,
- that handle is irreducible at kernel resolution,
- and multiple downstream elements depend on it.

Examples in the current project include bend, gauge, and ReID.

## 4. Elements
Elements are higher-order bundled roles built from kernel primitives and operators. They are justified only when several kernel primitives must repeatedly cooperate to realize a stable structural role. Elements are therefore downstream of kernel primitives, not siblings of them.

## 5. Runtime / support surfaces
Some components are neither deep ontological necessities nor canonical elements. They are runtime support surfaces: aggregation bridges, final action heads, routing helpers, or control layers. These should not be silently equalized with the strongest element nodes.

## 6. Kernel substrate
The kernel substrate is not a smuggled ready-made world-model. It is the bounded local unfolding currently maintained by a local structure inside change. It includes, at the current cut, things like:
- retained traces,
- active local comparisons,
- admissibility/tolerance structure,
- inherited stabilized embedding,
- and actionable continuation options.

The substrate is therefore the current locally held collapse of unfolding, not an independently given substance beneath process. See also the canonical statement [[01_Statements/02_Outer_Formation/017_S-DF-bounded-local-unfolding-operative-substrate]].

## Working rule
When a component is described in the repo, always ask:
1. Is this the ontological primitive?
2. Is this a first derived ontological necessity?
3. Is this a kernel-resolution primitive handle?
4. Is this an element (bundled role)?
5. Is this only a runtime/support surface?

Confusions among these levels create fake rigor and hidden smuggling.
