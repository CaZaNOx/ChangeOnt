# Payload rewrite intensity states how rapidly content attached to a stable scaffold becomes stale
## Content
Payload rewrite intensity measures how quickly the content attached to an otherwise stable scaffold becomes wrong, stale, or in need of replacement. This is not scaffold drift; it is rewrite on a carrier that may remain stable.

## Why this vector is needed
Without this distinction the system either erases too much when only payloads changed, or carries too much forward when the content should have been revised. Renewal forced this distinction into the open.

## Kernel relationship
High payload rewrite intensity weakens content-level carry-forward, raises revision pressure on currently attached support, and justifies preserving scaffold while replacing payload. Low payload rewrite intensity allows stronger continuation of currently attached support.

## Placement guidance
Ask: Given a stable carrier, how often do the values, assignments, route preferences, or local attached supports become stale? How quickly does content rewrite outpace the scaffold?

## Directional law
Increasing renewal frequency, nonstationary value drift, or attached-content turnover should raise this vector. Stabilizing assignments while leaving the scaffold fixed should lower it.

## Misuse warning
This vector is global only if it is measured by the same admissible logic across problems. It must not be replaced by family labels or by hidden oracle information. If a problem makes this vector hard to estimate, the right output is a wider region or lower confidence—not a family-specific guess.
